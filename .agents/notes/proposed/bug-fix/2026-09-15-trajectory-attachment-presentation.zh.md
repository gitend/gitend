# Agent Note: 统一 Trajectory 附件展示

Status: proposed

[English](2026-09-15-trajectory-attachment-presentation.md) | 中文

## 问题

用户消息可以包含文本、图片和普通文件，但 Trajectory 列表与详情面板展示的消息内容并不完整一致。[列表投影](../../../../packages/client/ui-trajectory/src/client/layout.ts)在消息含有文本时省略图片数量。[详情渲染器](../../../../packages/client/ui-trajectory/src/client/TrajectoryTable.tsx)在预览中展示图片而不展示普通文件卡片，在原始内容中又把文件 JSON 与渲染后的图片混排。读者需要切换视图才能确认完整的附件集合。

概述标签页通过紧凑展示选项嵌入 `MarkdownRecordContent`，预览标签页使用同一组件，但不启用该选项。附件调整必须保留这一共享渲染器，使两个入口展示相同的内容和操作。

## 提案

交付一项覆盖列表、概述、预览和原始内容的 Trajectory 展示调整。本文不实现所提议的行为；执行状态和已完成的验证证据由 Issue #4356 及其关联 PR（Pull Request）记录。

### 展示行为

| 位置 | 提议的行为 |
|---|---|
| 列表 | 在文本摘要旁分别显示非零的图片数量与普通文件数量，包含有文本的消息。每条记录保持为紧凑单行。 |
| 概述与预览 | 消息正文之后展示一个有序附件列表。两个标签页使用相同的附件渲染器；概述可以保留紧凑间距和滚动容器。 |
| 附件列表 | 使用等宽的紧凑行，统一行高、间距和圆角。左侧放文件类型图标或完整缩放的图片缩略图，右侧放已记录的名称与可用元数据。保留每次附件出现的顺序，包括重复引用。 |
| 图片交互 | 图片完整缩放到缩略图内，不裁剪。激活时打开现有大图查看器；保留键盘访问、加载反馈和读取失败后的重试。 |
| 原始内容 | 保留原始内容块顺序与边界。图片块和文件块使用一致、默认收起的元数据折叠区，展开后显示完整记录字段。文本块保持未渲染文本；生成的显示标签不进入原始字段。 |

有已记录文件名时使用文件名，否则为图片使用本地化的编号标签。类型与大小只在已记录数据支持时显示；保留零字节大小。长名称可以在视觉上截断，但完整名称必须能通过无障碍文本和工具提示获取。没有正文的消息仍须展示每个附件。多个附件在详情面板现有滚动区域内保持可达。

### 实现职责

[ui-trajectory](../../../../packages/client/ui-trajectory/README.zh.md)负责计数、有序附件投影和详情面板组合。通过其视图数据传递带类型的图片与文件引用，不从为展示准备的 JSON 中反向解析文件元数据。为原始内容保留完整的已记录附件字段。

[ui-attachment](../../../../packages/client/ui-attachment/README.zh.md)继续负责图片加载和查看器行为，使用 Conversation 拥有的会话级缓存。通过 slot 组合跨包 UI，并复用 [ui-primitives](../../../../packages/client/ui-primitives/README.zh.md) 中适用的静态控件，遵循[客户端规则](../../../../packages/client/AGENTS.md)。共享属性发生变化时，更新全部消费方。完整缩放处理限定于本次附件展示，并通过回归检查覆盖现有 Chat 和工具图片尺寸行为。

本次范围使用现有持久附件引用，不改变上传、存储、模型请求或会话格式，也不增加普通文件内容查看器或下载操作。样式遵循 [Web 样式规范](../../../../docs/web-styling.zh.md)；显示文字、无障碍标签和工具提示使用带类型的本地化字典。

### 现有决定

[通用文件上传决定](../../implemented/feature/2026-08-26-generic-file-upload.zh.md)继续负责上传、存储、准入和有序消息附件。本提案只调整其中的 Trajectory 展示，并不完整取代该记录。[不可读附件隔离提案](2026-08-20-attachment-read-quarantine.zh.md)处理模型请求恢复，与缩略图加载反馈相互独立。

## 考虑过的替代方案

**默认在详情面板中内联展示大图。** 这样可以立即阅读单张图片，但高图片会在窄面板中挤走附件名称和消息正文。紧凑行加显式图片激活入口能一致地概览混合附件。

**使用双列附件卡片。** 网格能在宽面板上突出缩略图，但会压缩长文件名空间，并要求窄面板采用不同排布。提案默认使用单列等宽列表。

**在原始内容中继续混排文件 JSON 和图片预览。** 这保留了现有渲染，却让同一个标签页对两种附件具有不同含义。一致的元数据折叠区用于检查已记录字段，图片视觉展示由预览负责。

## 验收标准

- 同时包含文本、一张图片和一个普通文件的消息，在列表显示两种数量，在概述和预览显示两个附件。
- 概述与预览共用一个附件渲染器；即使间距和容器不同，也提供相同的有序附件和图片操作。
- 纯附件消息、重复引用、无名称图片、零字节文件和长文件名保持可识别，不编造元数据。
- 图片完整缩放到紧凑缩略图内。键盘和指针用户均可打开并关闭现有图片查看器；图片加载失败时仍有可见反馈并可重试。
- 原始内容保留每个原始内容块及其顺序。图片与文件折叠区展示全部已记录附件字段，不以生成标签或下载的文件内容替代。
- 窄面板、两种主题和两种语言下均可使用。现有 Chat／工具图片行为和会话级图片缓存复用保留回归覆盖。
- 实现包含相应测试、经审阅的无密钥浏览器预期输出、双语文档，以及与演示 PR 当前提交对应的真实模型 GIF。

## 风险

在视图数据中加入文件引用，可能误将文件传给只接受图片的消费方，或丢失原始字段。需要跟踪每个受影响的类型标记，并验证混合与重复附件。紧凑缩略图降低了图表的直接可读性，因此大图激活入口必须容易发现。共享渲染器改动可能影响 Chat 和工具结果，概述滚动容器也可能遮挡末尾行；两者都需要组装浏览器检查。缺失的记录元数据必须保持明确缺失，图片读取失败不能隐藏其他文件。模型凭证不可用时，真实模型演示会受阻，必须如实说明，不能用 fixture（测试前置数据）录屏替代。
